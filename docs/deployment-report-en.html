01

Solution Overview

XIVI is an agentic localization pipeline that translates and dubs kids' animated video across multiple JAPAC languages, using Gemini (text / vision / native audio) as the intelligence core — no custom CV/NLP models are trained.

What sets it apart from a typical automated dubbing tool:

Character voice

Consistent across a series

Every character gets a character_id and its own voice profile, cross-referenced against earlier episodes so the voice never drifts mid-series — instead of one generic narrator voice.

Transcreation

Songs & rhymes

Lyrics are never translated literally — a dedicated prompt asks Gemini to preserve syllable count and rhyme, trading words as long as the rhythm survives. Harder than regular adult dubbing.

Safety & education

Cultural review + vocabulary

Every translated line is screened against market-specific cultural rules before approval, while vocabulary flashcards for parents/teachers are generated in parallel.

The system always keeps a human review step before publishing — no agent is allowed to auto-publish content for children.

02

System Architecture

The system is split into 2 independent Cloud Run services. The reason: api must respond fast (<1s) and scale with user traffic, while worker runs the long pipeline (translation, dubbing, video muxing — several minutes per video), receives work via a Pub/Sub push subscription, scales with job volume, and never has a user waiting on its HTTP response directly.

Managed services were chosen over self-hosted infrastructure throughout: Cloud Pub/Sub instead of Kafka (no cluster to operate, a push subscription calls the Cloud Run HTTP endpoint directly), Firestore instead of a hand-rolled WebSocket server (the onSnapshot SDK already exists, no reconnect/scaling logic to write), Memorystore Redis used strictly to cache Gemini results by hash(text + lang + mode) and to keep glossary terms translated consistently within a project.

03

Agent Pipeline

Every agent has a clear input/output and shares one interface — Agent.run(context) -> context (backend/worker/agents/base.py) — so agents can be added or removed without touching pipeline.py.

1

Ingestion & TranscriptionGemini multimodal (audio)

Extracts the audio track, produces a timestamped transcript and distinguishes speakers (diarization) → dialogue_lines[].

2

Character Voice ProfilingGemini multimodal (audio)

Analyzes voice characteristics (pitch, pace, speaking style) → assigns a consistent character_id, cross-referenced against prior episodes' voice profiles.

3

Translation & TranscreationGemini text — 2 prompt modes

Regular dialogue is translated in a tone appropriate for children; songs/rhymes use a dedicated transcreation prompt that preserves rhythm/rhyme instead of translating literally.

4

Cultural Safety CheckerGemini text — reasoning

Cross-references the translated line against cultural_safety_rules (a DB table per country, never hardcoded) → flags + a natural-language explanation; never auto-blocks — the final call belongs to the reviewer.

5

Dubbing / TTSGemini Native Audio

Generates audio that keeps intonation/emotion close to the original, per the character's voice profile; for songs, checks whether the clip's length matches the music's rhythm and requests a regeneration if it drifts past a threshold.

6

Audio-Video Muxffmpeg — not an AI agent

Muxes the dubbed audio clips into the original video at the correct timestamps, keeping picture/background music unchanged, replacing only the dialogue track.

7

Educational Content GeneratorGemini text — runs in parallel

Selects 8-12 age-appropriate vocabulary words, builds flashcards and 3-5 review questions, shown to parents/teachers in the dashboard. Not on the critical path.

Script-first variant (specs/003-script-first-ingestion): a job can start directly from a locked text script (CSV: segment_code,character_name,text) instead of a recorded video, so translation/dubbing can run in parallel with the video editor's own work. ScriptBenchmarkAgent takes Agent 1's slot, using the real Gemini Native Audio engine to measure spoken duration (then discarding that audio) in place of real footage; the Mux step (agent 6) is skipped entirely, and the job goes straight to ready_for_review with a downloadable audio bundle. A real video can be attached later via POST /jobs/{id}/attach-video, which re-runs only the mux step.
04

Main Request Lifecycle

Checkpoint/resume: after every agent, the worker writes current_stage to Cloud SQL before updating Firestore for the UI. If the worker crashes mid-pipeline (e.g. Cloud Run terminating it mid-processing), the next run resumes from the saved stage instead of starting over — avoiding re-paying for Gemini calls on steps already completed.

05

Gemini Integration

Every Gemini call in the system goes through one single wrapper — backend/worker/services/gemini_client.py. Agents may never import google.genai directly, so that retry/cache/rate-limit logic stays centralized in one place (Principle #3, AGENTS.md).

Two models in use

VariableModelUsed for
_TEXT_MODELgemini-3.6-flashTranslation, transcreation, cultural safety, educational content
_AUDIO_MODELgemini-3.1-flash-tts-previewDubbed audio generation per dialogue line (high-frequency TTS)

Models were chosen by calling the real REST API GET /v1beta/models directly to see which models are genuinely still available, then testing generateContent for real against several candidates — the SDK version pinned in requirements.txt returns 501 for models.list(), so it can't be trusted. The current choices avoid models Google has retired (404) or that carry a TTS quota too low to raise even with billing enabled (100 requests/day).

Cache + retry

Translation results are cached in Redis under translate:{hash(text)}:{lang}:{is_song}, TTL 24h — avoiding repeat Gemini calls when the worker retries after a network error, or when multiple episodes share the same line of dialogue (e.g. a recurring opening greeting). Model calls are wrapped in _call_with_retry, exponential backoff, capped at 3 attempts.

Choosing a character's TTS voice — 3 fallback tiers

build_voice_profile_metadata (shared by both the automatic flow and the flow where a user manually uploads a voice sample in the Character Voice Manager):

  1. Voice Design (client.voices.create, type="prompted") — Gemini listens to the sample, describes the voice characteristics in English, then synthesizes an entirely new TTS voice closely matching the original, not limited to a fixed voice set. Needs no consent_audio (unlike Voice Replication, which requires the actual voice owner to read a consent sentence themselves — not feasible for an existing video's original voice actor). If Google's own safety policy blocks it for sounding like a child's/minor's voice, the system deliberately accepts that and falls through to tier 2, rather than trying to work around it.
  2. Pick from Gemini's 12 built-in prebuilt TTS voices, matching the sample by gender/pitch/style.
  3. hash(character_id) — guarantees the same character always gets the same voice, with no guarantee it sounds like the original.

A failure at any tier must not fail the whole job.

06

Firestore — Realtime State

Firestore is not the source of truth for business data (that's Cloud SQL/Postgres) — it only holds the current job status for the UI to listen to in realtime via onSnapshot (frontend/src/lib/firebase.ts), instead of writing a custom WebSocket server and managing reconnects/horizontal scaling.

Each time the worker finishes a pipeline stage, it writes to two places: a checkpoint to the jobs.current_stage column in Postgres (to resume after a crash), and the same status to Firestore (so the UI sees it immediately). The GET /jobs/{id} endpoint on FastAPI is only a fallback for when the Firestore listener fails — not the primary source.

Firestore Security Rules (firestore.rules) and the hosting rewrite config (SPA fallback to index.html) are declared in firebase.json:

Cloud Deployment Flow

Infrastructure is stood up manually via infra/deploy.sh (the hackathon stage — no Terraform yet) for the 2 backend services, while the frontend deploys separately to Firebase Hosting as a static build — not through Docker/Cloud Run.

Backend — bash infra/deploy.sh <PROJECT_ID> <REGION>

1

Enable APIs & base infra

Enables Cloud Run, Cloud Build, Artifact Registry, Pub/Sub, Storage, Firestore, Cloud SQL, Secret Manager, IAM, Identity Toolkit; creates the GCS media bucket + CORS config (must include the Range response header so video/audio can stream from a signed URL).

2

Cloud SQL Postgres 16

Instance xivi-pg (tier db-f1-micro), creates the database + a dedicated app user (never root), auto-generates the database-url secret if missing.

3

Service account & IAM

xivi-run-sa — granted storage.objectAdmin, iam.serviceAccountTokenCreator (self-signs signed URLs via the IAM API since Cloud Run has no local private key), cloudsql.client, datastore.user, pubsub.publisher, secretmanager.secretAccessor.

4

Build & push images

docker build --platform linux/amd64 separately for Dockerfile.api and Dockerfile.worker, pushed to Artifact Registry — built by hand because gcloud run deploy --source can't pick the right Dockerfile when two live in the same directory.

5

Deploy the 2 Cloud Run services

xivi-api (allow-unauthenticated, min 0/max 10) and xivi-worker (no-allow-unauthenticated, 2 vCPU/2Gi RAM, timeout 3600s, concurrency 1 — video muxing is RAM-heavy and previously OOM'd at 512Mi).

6

Wire Pub/Sub → Worker

Creates the agent-events topic, a xivi-pubsub-invoker service account with run.invoker, a push subscription targeting only {WORKER_URL}/pubsub/push, ack-deadline 600s (Pub/Sub's push maximum) since the handler blocks until the whole pipeline finishes.

3 steps that can't be automated: (1) the gemini-api-key / redis-url secrets are third-party credentials (Google AI Studio, Upstash) an AI agent is not allowed to enter on the user's behalf; (2) Redis runs on Upstash's free tier instead of Memorystore, which needs its own account; (3) deploying the frontend to Firebase Hosting needs an interactive firebase login (OAuth) — done as a separate step.

Frontend — Firebase Hosting (static build, no Docker)

frontend/Dockerfile only runs the Vite dev server for local docker-compose — it is never used to build production. The real flow:

Because VITE_* values are baked into the bundle at build time, changing VITE_API_BASE_URL (e.g. the API moving region/project) always requires a rebuild and redeploy — the running static files can't pick up a new value on their own.

Most recent deploy (2026-10-12): built frontend/dist successfully (3 files, ~900KB JS, 248KB gzipped), ran firebase deploy --only hosting on project xivi-app — result: https://xivi-app.web.app, pointed at the API backend at https://xivi-api-765982386020.asia-southeast1.run.app (per VITE_API_BASE_URL in frontend/.env.production.local).

Technical Risks & Mitigations

RiskMitigation
TIMEOUTCloud Run timing out on long videos → split the video into scenes/chunks, process each chunk in parallel in the worker, stitch them back together at the end
RATE LIMITGemini Native Audio getting rate-limited → cache by (dialogue_line_id, target_lang, voice_profile_id) in Redis, avoiding repeat calls on retry
SYNCAudio/video drifting out of sync after dubbing → keep the original timestamps from transcription, align new audio to those timestamps instead of concatenating sequentially
CRASHWorker crashing mid-pipeline → checkpoint after every agent into jobs.current_stage, resume from the last stage instead of starting over
