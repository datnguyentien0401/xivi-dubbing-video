# XIVI Constitution

Immutable principles of the project. Every spec/plan generated by Spec Kit commands
MUST follow this constitution; any conflict with the constitution must be clearly
flagged and confirmed before proceeding.

## Core Principles

### I. Gemini is the core, not a supporting layer
Every new feature MUST be able to answer: "if we removed Gemini, would the feature
still have value?" If the answer is "yes, it would still work fine", then that
feature MUST NOT be considered core to the competition product. Do not train
custom CV/NLP models — every intelligence task (translation, safety review,
learning-material generation) MUST go through the Gemini API
(`backend/worker/services/gemini_client.py`).
**Why**: "Meaningful use of Gen AI" is a major scoring criterion of the
competition; a pipeline that uses Gemini only as a thin layer over manual logic
will lose points on exactly the most critical part.

### II. Humans always have final approval authority
No agent may automatically publish content intended for children without going
through review by a (human) content creator. Every long-running processing step
(translation, dubbing, safety review) MUST run asynchronously and stop at a
"pending approval" state before the result is considered final.
**Reason**: the product targets children's content — cultural/content safety
risk means AI can never be allowed to decide publication on its own.

### III. Use managed GCP services, avoid self-operated infrastructure
Do not add Kafka, self-hosted message brokers, or any infrastructure that
requires 24/7 self-operation unless there is a very clear technical reason that
Cloud Pub/Sub, Cloud Tasks, Cloud Run, or Firestore cannot meet (see
`docs/tech-stack.md` section 2 for an example of this reasoning). Preference:
Cloud Pub/Sub instead of Kafka, Cloud Run instead of self-managed servers,
Firestore instead of hand-written WebSockets.
**Reason**: a 2-3 person team over 3 weeks does not have the resources to
operate self-hosted infrastructure; the competition also requires the product
to be deployable to Cloud Run or Firebase.

### IV. Transparency of AI decisions
Every agent that makes an assessment/decision (especially the Cultural Safety
Agent) MUST return `reasoning` in natural language alongside the result label —
it must never return only `true`/`false` or a score with no explanation.
**Reason**: the content creator is the final decision-maker (Principle II) —
they need to understand why the AI flagged/did not flag a piece of content so
their approval is well-founded, not a blind rubber-stamp of the AI.

### V. Simplicity first, optimization later
Given the 3-week development constraint, every technical choice MUST prioritize
"simple, working, correctly scoped to the MVP" (see the "MVP scope for 3 weeks"
section in `docs/agent-pipeline.md`) over "feature-complete but risking missing
the deadline". Features outside MVP scope MUST be deferred, not silently folded
into scope mid-stream.
**Reason**: the competition deadline is fixed; a working demo with a narrow
scope scores higher than an unfinished system with a broad scope.

## Additional Technical Constraints

- **Unified agent interface**: every agent in `backend/worker/agents/` MUST
  follow the `Agent.run(context) -> context` interface (see
  `backend/worker/agents/base.py`). Do not merge multiple agents into one
  large function/class — each agent has a single responsibility and must be
  independently testable/replaceable. When adding a new feature → ask "is this
  a new agent or does it belong to an existing one?" before modifying an
  existing agent.
- **Do not hardcode business rules that can change** (e.g. country-specific
  cultural safety rules) — store them in the DB (`cultural_safety_rules`), not
  hardcoded in code.
- **Type hints/TypeScript types are required** in every language — do not use
  `Any`/`any` unless truly necessary, and with a comment explaining why.
- **Pydantic model for every input/output** in the Python backend — do not
  pass raw dicts between layers.
- **Do not build custom TTS/voice cloning** — use Gemini Native Audio or Cloud
  TTS.

## Development Process

- **Test before merge**: every new agent needs at least 1 test with sample
  input/output (no need to call real Gemini in tests — mock the response).
- **Commit message**: `<scope>: short description` with scope ∈ {`agent`,
  `api`, `worker`, `ui`, `infra`, `docs`, `specify`}. Example: `agent: add
  safety checker rules for VN/ID/PH`.
- **Do not commit secrets** (API keys, service account JSON) — use
  environment variables + `.env` (gitignored) or Secret Manager when
  deploying.
- **Code review required before considering a task done**: run the
  `code-reviewer` subagent against the project checklist (see `GEMINI.md`).

## Governance

This constitution takes precedence over every other convention (including
AGENTS.md and the tool-specific `GEMINI.md`/`*.md` files) in the event of a
direct conflict over principles; those files add operational detail and must
not contradict the Core Principles here.

**Amendment**: any change to this file MUST go through the
`/speckit-constitution` command, with a Sync Impact Report stating the old →
new version and which principle was changed/added/removed. Do not hand-edit
this file outside that process.

**Versioning**: follows semantic versioning — MAJOR when a principle is
removed or redefined in a backward-incompatible way; MINOR when a new
principle is added or a section is significantly expanded; PATCH for wording
clarifications/typo fixes only.

**Compliance review**: every spec (`/speckit-specify`), plan (`/speckit-plan`)
and task set (`/speckit-tasks`) MUST be checked against this constitution
before implementation; if a conflict is found, stop and seek confirmation
from the user before proceeding rather than interpreting it yourself.
